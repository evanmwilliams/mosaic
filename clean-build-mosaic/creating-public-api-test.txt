0. GOAL
------------------------------------------------------------------------------
Produce, for the SDDMM expression, a printout of EVERY rearranged schedule
("__Schedule N__") together with ALL of the external-library bindings that are
possible for that rearrangement -- i.e. the candidate set that exists BEFORE
Mosaic's automatic mapper makes its greedy "first match / first schedule"
choice. Constraints the user set: use Mosaic's public API, do NOT change the
original repository, make several library functions "available."


1. WHERE IT LIVES + WHY (faithfulness)
------------------------------------------------------------------------------
The file is in the project ROOT (clean-build-mosaic/), NOT inside mosaic/.
Reason: mosaic/test/CMakeLists.txt does `file(GLOB TEST_SOURCES *.cpp)` and
compiles ALL of them into one binary, `taco-test`. That binary already crashes
at static-init (a global in an existing test constructs + JIT-compiles a kernel
via Module::compile, which needs the Linux/x86 MKL artifact). So a new file
dropped into test/ would inherit that crash. A standalone executable that links
libtaco.dylib but pulls in none of the other test files avoids the crash.

Keeping it outside mosaic/ also leaves the clone byte-for-byte original:
   git status  -> no tracked source modified ; HEAD still be9deff
So the "faithful, unmodified upstream" property is preserved. The driver is
purely ADDITIVE and uses only public headers.


2. THE PIPELINE IT MIRRORS (the white box)
------------------------------------------------------------------------------
Mosaic's automatic mapper, in src/index_notation/index_notation.cpp:

  concretizeAccelerated()            (:2291)
    stmt = makeReductionNotation(stmt) if einsum                 (:2294-2296)
    std::vector<IndexStmt> stmts = autoAccelerate(stmt, funcs)   (:2298)
    stmt = stmts[0]   <-- GREEDY: take the first schedule        (:2299)

  autoAccelerate()                   (:4915)
    possibleRewrites = generateEquivalentStmts(stmt, 3)          (:4919)
      ^ the "rearrange the expression many ways" step; element [0] is the
        original stmt; depth 3 applies identity/commutativity/distributivity/
        common-term rewrites repeatedly.
    for each rewrite: helperCheckForMatches(rewrite, funcs, ...) (:4928-4930)

  helperCheckForMatches()            (:4801)
    for each function f:                                          (:4812)
      matched = allMatchedOpPatterns(stmt.rhs, f.reductionRhs)    (:4821)
      for each matched sub-expr:
        if hasPreciseMatch(sub, f.reductionRhs).possible:         (:4830-4831)
          replace sub in the statement with a workspace + bind f  (:4850-4853)
      ^ GREEDY #2: the FIRST function (registration order) to match a given
        sub-expression replaces it; a later function matching the SAME
        sub-expression finds nothing left to replace (no-op).

So there are TWO greedy decisions: (a) stmts[0] across schedules, and (b)
first-matching-function per sub-expression inside each schedule. Both hide the
alternatives. This driver re-runs the enumeration WITHOUT either collapse.


3. WHAT THE DRIVER ACTUALLY DOES (step by step)
------------------------------------------------------------------------------
(a) Build SDDMM:
       A(i,k) = B(i,k) * sum(j, C(i,j) * D(j,k));
    B is CSR (the sparse "sampling" mask); C,D dense. Taken from the upstream
    test `timeEndToEndMMSDDMM` (test/test-time-search.cpp:257) so the algebra
    is identical to how Mosaic itself exercises SDDMM.
       IndexStmt stmt = A.getAssignment();
       if (isEinsumNotation(stmt)) stmt = makeReductionNotation(stmt);
    This is the exact normalization concretizeAccelerated does.

(b) Make functions "available" -- registered as a vector<FunctionInterface>:
       Saxpy          x(i)=x(i)+y(i)                 (cblas_saxpy)
       Sdot           s = x(i)*y(i)                  (cblas_sdot)
       MatrixMultiply z(i,k)=x(i,j)*y(j,k)           (cblas_sgemm)
       BlasSymmLeft   z(i,k)=x(i,j)*y(j,k)           (cblas_ssymm)
       Sgemm          z(i,k)=x(i,j)*y(j,k)+z(i,k)    (cblas_sgemm, w/ accumulate)
    MatrixMultiply AND BlasSymmLeft have IDENTICAL bare-matmul semantics, so
    BOTH precisely match SDDMM's inner sum(j, C(i,j)*D(j,k)). That is the
    "one sub-expression, two functions" case, chosen on purpose so the output
    visibly contains a candidate the greedy path would throw away. Sgemm's
    "+z(i,k)" accumulate makes its pattern NOT match the bare inner product, so
    it shows a registered-but-non-matching function. Only cblas_interface.h is
    needed (no MKL/GSL/TBLIS headers), keeping the build self-contained.

(c) Per-function reference pattern (referenceRhs()):
       getStmt() -> to<AcceleratorAssignment> -> makeReductionNotation -> getRhs()
    This is helperCheckForMatches lines 4813-4821 verbatim, so the matcher sees
    each function in the same reduction notation Mosaic uses internally.

(d) Enumerate schedules:
       std::vector<IndexStmt> forms = generateEquivalentStmts(stmt, 3);
    The SAME call autoAccelerate makes. Each element == one candidate schedule
    (rearrangement). Duplicates are de-duped by printed string for readability;
    every distinct rewrite is still shown.

(e) For each schedule, list ALL possible bindings (the pre-greedy candidate
    set) by calling Mosaic's OWN public matcher with a FRESH per-schedule
    catalog set:
       std::set<std::pair<std::string,std::string>> catalog;
       form.helperCheckForMatches(form, functions, catalog);
    helperCheckForMatches runs BOTH match strategies:
       1. precise match (allMatchedOpPatterns + hasPreciseMatch) -> these BIND
          into the lowered statement.
       2. hold-constant match (makeCombi/toMatchVars, index_notation.cpp
          4856-4899) -> CATALOGUED as possible but NOT structurally bound.
          This is how a 1-D dot product (cblas_sdot, s = x(i)*y(i)) matches the
          j-contraction sum(j, C(i,j)*D(j,k)) -- by holding i,k constant.
    The catalog therefore is the COMPLETE candidate set. We separately compute
    the default pick (first PRECISE/direct match in registration order), which is
    what actually binds, and tag each catalog entry "[DIRECT bind: order matches]"
    vs "[via TILING/fix: order-reduced map]" (the paper's bind vs map). A schedule
    with no matches is labelled "(none -- pure TACO)".

    CORRECTION HISTORY: the first version of this driver did ONLY strategy 1
    (precise) and so MISSED every cblas_sdot match -- it reported 2 matching
    functions when Mosaic actually finds 3. Verified against ground truth by
    calling stmt.autoAccelerate(stmt, fns) directly, whose printed catalog lists
    exactly 6 pairs: {C*D, D*C} x {sdot, sgemm, ssymm}. The corrected driver
    now reproduces those 6 exactly by delegating to helperCheckForMatches rather
    than reimplementing the file-local (static) hold-constant helpers.


4. THE ONE NON-HEADER DETAIL (still no source edit)
------------------------------------------------------------------------------
generateEquivalentStmts has three overloads in libtaco; only the 1-arg form is
declared in the public header (index_notation.h:223). autoAccelerate uses the
(IndexStmt,int) depth overload, which exists in the compiled library but is not
header-declared. The driver forward-declares it:
       namespace taco { std::vector<IndexStmt> generateEquivalentStmts(IndexStmt,int); }
This only declares access to an EXISTING exported library symbol (libtaco.dylib
is built with default symbol visibility). No upstream file is modified; we are
just calling the same function autoAccelerate calls, at the same depth (3).


5. WHY THIS RUNS ON macOS arm64 (when taco-test cannot)
------------------------------------------------------------------------------
Every API used -- generateEquivalentStmts, allMatchedOpPatterns,
hasPreciseMatch, getStmt/makeReductionNotation -- is pure index-notation
analysis. None call Module::compile(). So the x86/MKL/CUDA JIT wall is never
hit. (hasPreciseMatch is purely structural; it does not even invoke Z3. Z3 is
only used by Mosaic's dynamic-constraint check, which none of these cblas
functions declare.) A minimal libtaco-linked program was verified to load
cleanly first, confirming the crashing global lives in the test files, not the
library.


6. BUILD + RUN
------------------------------------------------------------------------------
Compile (from clean-build-mosaic/):
   clang++ -std=c++14 -I mosaic/include -I mosaic/build/include \
       SDDMM-public-api.cpp -L mosaic/build/lib -ltaco -o SDDMM-public-api

Run (libtaco.dylib is a shared lib, so point the loader at it):
   DYLD_LIBRARY_PATH=mosaic/build/lib ./SDDMM-public-api

Output is also saved to logs/SDDMM-public-api-output.txt.


7. WHAT THE OUTPUT SHOWS (observed result)
------------------------------------------------------------------------------
- 904 distinct schedules (rearrangements) printed, each as "__Schedule N__".
  This count is DETERMINISTIC (verified over 4 runs).
  (Historical note: an earlier capture appeared to show only 88. That was a
  LOGGING ARTIFACT -- the run was piped `| tee file | head -80`, and head
  closing the pipe SIGPIPE-killed tee mid-write, truncating the file at ~88
  schedules. The driver always produced the full set; re-running with a plain
  `> file` redirect shows 904.)
- Schedule 1 (the original form) lists THREE valid mappings for the SAME
  sub-expression (matching Mosaic's full matcher; paper terminology):
       sum(j, (C(i,j) * D(j,k)))  ->  cblas_sdot    [via TILING/fix: order-reduced map]
       sum(j, (C(i,j) * D(j,k)))  ->  cblas_sgemm   [DIRECT bind: order matches]
       sum(j, (C(i,j) * D(j,k)))  ->  cblas_ssymm   [DIRECT bind: order matches]
  and reports ">> default pick (no autoscheduler; first direct bind): ... ->
  cblas_sgemm" (registration order: MatrixMultiply before BlasSymmLeft).
  cblas_sdot (a 1-D dot product, s=x(i)*y(i)) maps only after order-reducing the
  j-contraction by holding i,k constant -- this is the paper's `map`/`.fix`
  tiling (Fig 2-3, Sec 5; search Step 4 "Tiling Validation", Fig 9-10). This
  implementation catalogs it as a valid mapping but realizes the structural bind
  only for the DIRECT (order-matching) cases.
- Catalog breakdown over all 904 (DISTINCT pairs = 6, matching autoAccelerate
  ground truth exactly): {sum(C*D), sum(D*C)} x {cblas_sdot, cblas_sgemm,
  cblas_ssymm}. Occurrence tally: each of sdot/sgemm/ssymm appears 171 times
  (every binding schedule lists all three for its present product order).
- Default-pick breakdown over all 904: 733 pick nothing (pure TACO), 146 ->
  cblas_sgemm on sum(j,(C(i,j)*D(j,k))), 25 -> cblas_sgemm on the commuted
  sum(j,(D(j,k)*C(i,j))). So 171 schedules pick a direct bind, always the first
  one (cblas_sgemm); cblas_ssymm and the tiled cblas_sdot are not selected.
  Per the paper, Mosaic's search RETURNS all valid mappings and leaves ranking
  to an autoscheduler ("future work", Sec 3/6) -- so "first" is just the default,
  not a quality decision.
- Two interface classes (MatrixMultiply and Sgemm) both report
  getFunctionName()=="cblas_sgemm", so they are indistinguishable by name in the
  catalog. For SDDMM only MatrixMultiply matches (Sgemm's z=x*y+z accumulate does
  not match the bare inner product), so this name collision is cosmetic here.
- Registered functions Saxpy (x=x+y) and Sgemm (z=x*y+z) never appear in the
  catalog -- correctly, since SDDMM has no top-level additive structure matching
  saxpy and no accumulate matching Sgemm. Only sdot/sgemm/ssymm-shaped functions
  match the dense-dense contraction.
- IMPORTANT -- the 904 is dominated by trivial rewrites: 891/904 contain
  identity/zero insertions (x+0, x-0, x*1, and distributive *0). Only 4 are
  structurally distinct algebra, and all 4 are commutativity reorderings of the
  SAME computation:
       B(i,k) * sum(j, C(i,j)*D(j,k))     (original)
       B(i,k) * sum(j, D(j,k)*C(i,j))     (commute inner product)
       sum(j, C(i,j)*D(j,k)) * B(i,k)     (commute outer product)
       sum(j, D(j,k)*C(i,j)) * B(i,k)     (commute both)
  The blow-up to 904 is BY DESIGN: generateEquivalentStmts deliberately inserts
  identity/zero rewrites and recurses to depth 3, because such forms can expose
  matches for functions whose semantics include identities (e.g. the
  accumulating Sgemm  z=x*y+z  matching a "...+0" form, or saxpy x=x+y matching
  an additive form). So 904 faithfully reflects the algorithm, but is a poor
  proxy for "number of meaningful schedules" (~4, modulo identity+commutativity).
- Schedules whose rewrites perturb the inner product (e.g. inserting (C+0))
  lose the structural match and are shown as "pure TACO" (no binding) --
  illustrating that rearrangement directly changes which bindings are reachable.
- The temp-dir banner libtaco prints at startup is harmless: it does NOT
  compile anything.

8. FAITHFULNESS TO THE MOSAIC PAPER (PLDI 2023, PACMPL 7(122))
------------------------------------------------------------------------------
Bansal, Hsu, Olukotun, Kjolstad, "Mosaic: An Interoperable Compiler for Tensor
Algebra." Read locally via pdftotext; key cross-checks:

- SDDMM is the paper's OWN running example: A(i,j)=B(i,j)*C(i,k)*D(k,j)
  (Sec 2, Fig 2-4, Fig 9-10). Our driver uses the same kernel.

- Three ways to target a function (Sec 5), all reflected by the driver:
    * bind  (full schedule)  -> user fixes transforms + function explicitly.
    * map   (partial schedule) -> "Mosaic will automatically discover a valid
                                   binding (if possible) by tiling and reshaping
                                   the tensors ... to match the constraints of
                                   the function." == our "via TILING/fix" maps.
    * automatic search (Sec 6) -> "search the space of possible mappings and
                                   return a list of valid schedules. Then the
                                   user can select one schedule out of all."
  Fig 2's bind schedule literally contains ".fix(iw,jw)  // Consider iw, jw to
  be constant" -- i.e. holding outer index vars constant is the paper's own
  mechanism, identical to the code's hold-constant matching (toMatchVars).

- Automatic search = 5 steps (Fig 9), which the driver mirrors:
    1 filter by datatype;
    2 mathematical rewrites: "Add Identity (Zero Matrix)" + Commutativity +
      Distributivity (Sec 6.1)  == generateEquivalentStmts(stmt,3). This is why
      891/904 schedules are identity/zero rewrites -- it is a DELIBERATE paper
      step (exposes matches for functions with additive identities), not noise.
    3 "Tensor Index-Variable Matching ... resolving conditions on tensor order"
      == allMatchedOpPatterns + hasPreciseMatch (our DIRECT binds).
    4 "Tiling Validation": order-reduce a sub-expr (e.g. j==4) so a lower-order
      function fits, checked by SMT  == the hold-constant branch + GenerateSMTCode
      (our "via TILING/fix" maps, e.g. 1-D cblas_sdot onto the j-contraction).
    5 return ALL valid mappings.

- No autoscheduler: "The automatic-mapping solution only returns a list of valid
  mappings; users can add an autoscheduler that ranks ... We leave this
  autoscheduler as future work." (Sec 3/6). So our "default pick = first" is
  faithful: ordering decides because no ranking exists.

- SMT validation: "validates mappings by translating constraints defined on
  tensor order and dimension to an SMT query" (Sec 3, Sec 6) == GenerateSMTCode
  -> python3/z3. Not triggered by the cblas functions here (no constraints), but
  the path is present and used by Step 4 for tiled maps.

NET: the corrected driver is faithful to BOTH the repo (it calls Mosaic's own
helperCheckForMatches, no reimplementation) and the paper (it reproduces the
5-step search incl. tiling/order-reduction, and presents bind/map/tiling and
"all valid mappings, no autoscheduler" using the paper's own vocabulary).
